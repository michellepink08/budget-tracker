# Plan 38 — Financial Integrity, Design System v2, Voice/Receipt Intelligence & Test Infrastructure (Staged Roadmap)

**Status:** In progress. This is a decomposition of one very large request into ordered, independently-shippable stages — the same approach used for the original mega-request at the start of this project (which became Plans 20–27). Each stage is verified (typecheck/lint/test/build + live check) before the next begins, per the request's own "implement in safe stages" instruction.

**Source:** A single user message specifying 14 numbered requirement areas. Reproduced/mapped below against what a codebase inspection found already exists vs. is genuinely new work — this mapping is the actual deliverable of the "create an implementation plan" step, since roughly a third of the request turns out to already be satisfied by construction, and pretending otherwise would mean re-doing settled work.

## Fact-finding summary (full detail in the session's inspection pass)

- **Shared source of truth (§1):** Already true by construction. `computeAccountBalance`, `computeDisposableTotal`/`computeSavingsTotal`/`computeConfirmedReserves`, `listRestrictedFundGroups`, `listCalendarEntries`, Year Plan's reserve math, and every report all derive from `Transaction` rows — nothing maintains a separately-stored total. Planning records (`ShoppingList`, `Receipt` drafts, `IncomeForecast`, suggested transfers) never write to `Account`/balance fields — verified in this session's own work on Plans 22–25. **Real gaps found:** (a) multi-record mutations (transfers, `confirmReceipt`, `markPayablePaid`, credit-card payment, recurring confirmations) are sequential `await`s, not wrapped in `prisma.$transaction(...)` — a mid-sequence failure could leave a partial write; (b) suggested transfers (`getRecommendedFundingTransfer`) return only `{fromAccountId, toAccountId, amount}` — no `reason`/`obligations`/`remainingBalance` fields; (c) restricted-fund "upcoming obligation" already sums *every* unpaid payable via `listRestrictedFundGroups`'s dedup logic, not just the next one — this part of §1 needs no change, just a named test proving it.
- **Voice approval commands (§2):** Quick Capture already has a draft→confirm→execute pipeline, a one-clarification-at-a-time ambiguity mechanism, and single-shot undo (`QuickCaptureLog` + `undoExecution`). **Gap:** the specific phrase set ("Approve and save," "Mark this as paid," "Undo that," etc.) isn't wired as recognized commands, and undo doesn't cover manually-created (non-Quick-Capture) records.
- **Receipt alias learning (§3):** **100% new.** Confirmed no name-matching, confidence tiers, or alias-reuse exists anywhere in the receipts code path today — `addLine`/`updateLine` take whatever `catalogItemId` the UI passes, full stop. The `Alias` model already supports `kind: "shopping_item"` (added in Plan 23) but nothing writes/reads it for receipts.
- **Design tokens v2 (§4) / app-wide audit (§5) / income-expense colors (§6):** The current palette (Plan 20, wine/berry) does not match this request's new hex values (e.g. current `--primary` #6F1D3A vs. requested #721D42; current disposable/savings/restricted accents are different hues than requested). This is a **deliberate palette replacement**, not a bug fix.
- **Left nav redesign (§7):** Current `SideNav`/`NavDrawer` are functional but plain — gradient/glow/hover-lift treatments genuinely don't exist yet.
- **Sign-out bug (§8):** **Confirmed real, reproduced in code.** `SignOutButton` in `SideNav`'s footer is never conditionally hidden/adapted for the collapsed state — only nav-link *text* is hidden when collapsed; the sign-out button's own layout doesn't adapt, matching the reported "floats/orphaned" bug exactly.
- **Dropdown dark-mode (§9):** Inspected `select.tsx` and `dialog.tsx` (the only portal-based overlay components that exist) — both are fully token-driven with correct `dark:` variants already; **no `dropdown-menu`/`command`/`popover` component exists in this codebase at all.** This section may already be satisfied for what exists today; verified with an explicit test/manual pass rather than assumed.
- **Form fields (§10):** Confirmed flat — `input.tsx`/`textarea.tsx` use `bg-transparent`, no shadow, relying on the parent surface. Matches the reported "too flat" complaint exactly.
- **Audit history (§11):** No general `AuditLog` model exists — only `QuickCaptureLog`, scoped to Quick-Capture-originated writes only. Manual form edits (the majority of mutations in this app) are not logged anywhere. **This is the largest single piece of new work in the whole request** — every mutation call site needs an audit write.
- **Testing (§12):** **No integration or e2e layer exists at all** — only Vitest unit tests (77 files). No Playwright/Cypress/Testing-Library dependency installed. Building this from zero, plus 20 specified e2e journeys, is itself a multi-day-scale effort on its own.
- **Invariants (§13):** Several have solid existing coverage (restricted-fund exclusion, payable duplicate-payment rejection); several have **no test that names the invariant directly** even though the underlying behavior is likely correct (transfer exclusion from income/expense totals, credit-card-payment non-double-counting) — worth closing as named, explicit tests regardless of whether the behavior already happens to be right.
- **Definition of Done (§14):** A process checklist to apply per-stage below, and a final completion report once all stages are done.

## Staging (ordered; each stage gets its own detailed sub-plan doc as it starts, mirroring plan-28..37's pattern)

1. **Stage A — Financial integrity audit & invariants** (this session, starting now): wrap genuinely multi-record mutations in `prisma.$transaction`, enrich suggested-transfer output shape, add the named invariant tests §13 asks for (closing real coverage gaps found above), add a restricted-fund "all unpaid payables, not just next" regression test.
2. **Stage B — Sign-out layout fix** (§8): small, isolated, high-confidence bug fix.
3. **Stage C — Design tokens v2** (§4): replace the token values in `globals.css` with the new palette, both modes. Foundational for D/E/F.
4. **Stage D — App-wide card/color audit** (§5, §6): re-skin existing cards/badges to the new semantic mapping (income=blue, expense=coral, savings=violet, restricted=amber, etc.) across every page named in §5.
5. **Stage E — Left nav redesign** (§7): gradient, hover/focus motion (respecting `prefers-reduced-motion`), collapsed-state tooltip, mobile scroll behavior.
6. **Stage F — Dropdown & form-field polish** (§9, §10): verify §9 is already satisfied or fix what isn't; raise form-field surfaces per §10.
7. **Stage G — Audit history** (§11): new `AuditLog` model + a thin `recordAudit(...)` helper wired into every mutation path. Largest schema/plumbing stage.
8. **Stage H — Receipt alias learning** (§3): confidence-tiered matching (saved names → merchant aliases → past corrections → size/price/similarity), the one-short-clarification-question UX, alias save-on-confirm.
9. **Stage I — Voice approval command set** (§2): wire the specific phrase list to the existing confirm/undo pipeline; extend undo to cover manually-created records where feasible.
10. **Stage J — Test infrastructure** (§12): install Playwright, write the integration tests, write the 20 e2e journeys against the now-complete feature set.
11. **Stage K — Final Definition of Done pass & completion report** (§14).

Stages G, H, I, and J are each large enough to warrant their own full brainstorm→spec→plan cycle (matching this session's established practice for Year Plan/Shopping/Receipts/Calendar) rather than being fully designed inline here — this document commits to the order and the scope boundaries per stage, not to every implementation detail of stages not yet started.
